# UU Remote helper protocol review — research and implementation gates

**Status (2026-11-12):** research notes and offline-only contracts, **not** a UU client, working login, registered helper or cloud listener. No user credential or network packet was used while building the registration/message parser. Existing PR #16 (official router `uuplugin` experiment) is unchanged.

## Evidence boundaries

[Keithin's Z4 report in Issue #15](https://github.com/coolhpj/uu-remote-wol-router-helper/issues/15#issuecomment-6820635855) describes a non-gateway x86_64 NAS running a **third-party UU Remote Linux host identity**, not the router `uuplugin` identity. The reporter says it registered as a wake helper, received a cloud `wake_on_lan` command, emitted Magic Packet and survived a whole NAS reboot. These are third-party **device** observations; we have not independently reproduced their service protocol or live WOL.

Public protocol observations from [VallierDev/uu-remote-linux](https://github.com/VallierDev/uu-remote-linux) (GPL-3.0; **do not copy implementation code into this MIT repo**) and [its registration-field fix `fe052cdc`](https://github.com/VallierDev/uu-remote-linux/commit/fe052cdca7ad90d1ab7c27d031036b1071869070) suggest the following steps. These are reverse-engineered community observations, **not an official, stable vendor API specification**.

## External dependencies and stages not implemented

| Stage | Observed protocol clue | Required independent proof |
|---|---|---|
| Device enrollment | Device initialization before QR login (reported endpoint `/api/v1/device/windows/init`) | Explicit host identity, no unauthorized automatic registration |
| QR sign-in | QR generation, status polling and owner confirmation (reported `/api/v1/qrcode/gen/login`, `/api/v1/qrcode/login/status`, `/api/v1/login/by_qrcode`) | Owner actually scans/authorizes, retry/expiry safety, no token/QR logging |
| Room creation | Authenticated account creates a signaling room (reported `/api/v1/room/create`) | Live response, server identity/TLS, room token expiry and refresh |
| Helper registration | Report `mac`, `ip`, `inner_ip`, `subnet_mask` to a helper info endpoint (reported `/api/v1/device/wake_on_lan/info`) | Real account-accepted HTTP 200 + business code 0 and service-side helper enablement |
| Cloud command | Socket.IO / Engine.IO room push `bmsg_push` with `type=wake_on_lan` and `target_device` | Authenticated room and validated push, not merely a local JSON fixture |
| Real wake | MAC and LAN identity validated against local user-owned targets; one directed LAN Magic Packet | Real PC offline→online over mobile data, plus post-reboot identity reuse |

The publicly described REST authentication signs a canonical request using HMAC-SHA256 over HTTP method, path, sorted lowercase `x-param-*` request headers (excluding the signature field) and the exact request body bytes. QR generation is a POST with an **empty body**, unlike an encoded `{}`. The QR-status query uses the `status_query_ticket` from QR generation, with last-known numeric status; the observed states are `1` pending, `2` scanned, `4` approved and `0`/`3` request a new QR. The Socket.IO transport is reported as Engine.IO v4 (not a generic JSON WebSocket). These are **indirect observations from a GPL-licensed community implementation**, not independently established vendor specifications. Our separate `vendor-wire-contract.mjs` reimplements the wire-format contract without copying that implementation or hardcoding a signing key, and is currently offline-test-only.

**No embedded client secret, signing key, cookies or third-party source code should be copied into this MIT experiment.** API status, session identity, token rotation and actual field shapes must be verified with the owner's account before claiming compatibility. A normal `HTTP 200` or an established WebSocket is not proof that remote wake works.

## What is actually implemented

- `cloud-contract.mjs` (Node 22 development harness): deterministic, **network-free** registration-body validator, HTTP/business-result checker and Socket.IO `bmsg_push / wake_on_lan` frame validator. It requires a future caller to provide a *verified* account/room state, an accepted helper registration and explicit WOL enablement. It then enforces an **owner-configured exact MAC+IP allowlist**, LAN subnet/mask and produces **inert** wake instructions. Caller-supplied boolean state in an offline fixture **does not establish actual authentication**.
- `tests/test-remote-helper-cloud.mjs`: normal/invalid protocol, wrong account, unknown target, expired/unconnected room, wrong mask, illegal MAC/IP, malformed or oversized messages.
- `tests/test-remote-helper-cloud-bridge.mjs`: simulated accepted registration and an artificial cloud frame flowing to `wol-send.sh` with **fake `ip` and `socat`** in a temporary directory. This proves the two local modules' data shapes and 102-byte WoL format compose, **not actual cloud delivery**.
- `vendor-wire-contract.mjs` and `tests/test-remote-helper-vendor-wire.mjs`: offline, caller-key HMAC-SHA256 canonicalization and QR status-query-ticket/state decoding, with an explicit API path allowlist, no real endpoint request, and negative tests for legacy tickets, body differences and untrusted headers. This is a *candidate* request format only.
- `enrollment-state.mjs`, `private-credentials.mjs`, `fixture-qr-client.mjs` and `fixture-room-client.mjs` implement a strict **local mock** of enrollment, one-time QR exchange, private atomic token storage (0600, **plaintext not encrypted**) and account/room-bound WebSocket event processing. They do not know the vendor's real signature algorithm or network endpoint and accept only loopback test servers. The state machine's approval bit and a synthetic `room_ready` acknowledgement are only fixture observations, **not proof of a real user or UU server identity**. Tests reject QR expiry/replay, unwanted approvals, wrong account/token, extra permissions, symlinked token stores, premature/forged push and room disconnect. Room login by itself is not registration: the fixture requires separate accepted registration evidence plus explicit WoL enablement, both of which must later originate from authenticated vendor transport. There is **no** real UU QR client, vendor-authenticated/TLS signing transport, service-side registration, vendor Socket.IO room subscription, persistent room reconnection, token rotation or live-cloud device discovery. The Node harness is not the final selected production runtime; routers with tight memory must not be forced to install a full remote desktop or Node environment.

## Engine.IO v4 / Socket.IO envelope acceptance (offline-only candidate)

An independent fixture-only decoder in `engineio-v4-transcript.mjs` now checks the public protocol envelope: initial Engine.IO `0` open metadata with bounded ping intervals, Socket.IO `40` namespace connect acknowledgement, a numbered `42` room-info request / matching `43` acknowledgement, Engine.IO server ping `2` / client pong `3`, disconnect and `42` event decoding. It enforces heartbeat expiry, malformed-message fail-closed behavior, and refuses to infer account or room authentication from a parsed frame. A `bmsg_push` is returned as inert, **untrusted** data until a separate real authenticated signaling transport establishes the vendor token, TLS identity, account binding and accepted helper registration. Sixteen isolated tests exercise this envelope, including a Socket.IO `44` namespace-connection rejection. This is based on publicly observable protocol shapes, **not** an implementation or a replay of third-party GPL client code, and it has not connected to the real UU signaling server.

## Real loopback Engine.IO / Socket.IO frame acceptance (test-only)

`fixture-engineio-socket.mjs` is an independent Node 22 test-only session driver layered over the existing `engineio-v4-transcript.mjs`. The injected WebSocket is pinned to a single a dynamically allocated numeric-loopback WebSocket test server at the Engine.IO v4 path, **not** the actual approved WSS domain. The `X-NRD-AUTH` vendor room token and WSS upgrade URL are passed only as sensitive, in-memory **inspection metadata**; they are not transmitted in the Node built-in WebSocket HTTP upgrade. Seventeen real-loopback tests verify the OS actually exchanges 0/40/4211/4311 and 2/3 frames, pre-ACK event rejection, malformed frame rejection, explicit Socket.IO 44 error, disconnect handling, bounded heartbeat, and single-use room tickets. Reconnect requires a different fresh bearer and a new explicit fixture authorization. Old socket callbacks cannot affect the new connection. Public status always remains `authenticated=false`, `registrationVerified=false`, `wakePermitted=false`, and no code sends WOL. This does **not** prove real NetEase TLS identity, bearer-header authentication, cloud event provenance, or any physical device wake.

## Authorized external signing boundary (no vendor key bundled)

Our independent MIT request-format adapter now supports an explicitly opt-in **external signing callback** and the existing caller-provided-key HMAC without duplicating canonicalization. The caller is responsible for providing a permitted provider; this repo neither obtains a vendor key nor ships a signer service. The canonical challenge can contain sensitive identifiers and must not be logged; exceptions are redacted, callbacks have a bounded timeout/abort signal, invalid signatures are rejected and a signing callback is never used for unlisted API paths. The HTTPS adapter rejects a simultaneous local key and external provider and still requires an explicit opt-in, valid timestamps, TLS and mock-only CI. Sixteen new synthetic tests prove canonical parity and failure isolation; no real UU connection is made. The source decision and security audit are in [AUTH-SOURCE-DECISION.md](AUTH-SOURCE-DECISION.md). The official NetEase mobile URL Scheme integration guide does not document a headless helper API or legal signing provision, and the GPL sidecar docs still include non-WOL remote terminal/file access. Both routes remain **unverified/blocked for WOL-only release**.

## Synthetic TLS/WSS Upgrade with a real on-wire fixture-only bearer

`fixture-wss-upgrade.mjs` uses Node TLS directly to connect **only to numeric loopback** (no public DNS or vendor connection) and verify a synthetic server certificate chain, SNI hostname, approved WSS plan, and `http/1.1` ALPN before sending a **synthetic-only** `X-NRD-AUTH` header in a real WebSocket Upgrade request. The server's `101`, `Upgrade`, `Connection` and challenge-derived `Sec-WebSocket-Accept` must all match. The transport is default-disabled and accepts only explicitly tagged synthetic fixture room tickets. Fifteen new real-TLS fixture tests cover rejected/untrusted/wrong-host certificates, wrong ALPN, HTTP deny/redirect, forged or duplicated WebSocket acceptance, oversize response, expired candidate and short timeouts. Test keys/certificates are generated at runtime by OpenSSL under temporary private storage and deleted; **none** are distributed, stored as CI secrets or used against UU. All status output is redacted and expressly marks `authenticated=false`, `registrationVerified=false`, `wakePermitted=false`. Even when the synthetic server accepts the header, this is **not** genuine NetEase cloud authentication or helper registration.

## Independent room-create candidate validation (disabled by default)

The separate `vendor-room-contract.mjs` now checks the publicly described `/api/v1/room/create` response shape (`signaling_server`, bearer `token`, optional `signaling_list` and `ws_connect_timeout_ms`) without copying third-party implementation code. It requires HTTP 200 + business code 0, an exact preapproved WSS hostname and bounded freshness/timeout, rejects token/header injection and obviously expired JWT-shaped bearer values, and keeps sensitive credentials out of the public status. The existing HTTPS adapter can issue an opt-in, signed `{}` POST and return only an inert, explicitly untrusted room candidate. It **cannot** verify the signature or authorization of a JWT without trusted keys, establish server identity without a real TLS connection, or infer actual cloud-room authorization from the shape or a `room_info` frame. The expected signal host must be supplied by an independently trusted policy; the server response must never choose its own allowlist. All current tests are offline and use synthetic credentials.

## Next acceptance gate (no community waiting required)

1. Independently verify the real UU vendor's QR/login request-signing, TLS identity, session expiry and room Socket.IO protocol; the current loopback HTTP/WebSocket handshake is test-defined, not a vendor implementation. Avoid copying GPL third-party code or embedding vendor secrets.
2. Design real transport credential lifecycle, secure refresh and restart behavior, account-bound target allowlist storage and container capabilities. The 0600 atomic store is a test-only building block; it is not encryption and actual long-term secret protection remains to be reviewed.
3. Only with the owner's explicit participation, perform first QR login and official app helper registration; observe sanitized categories, not tokens. Confirm cloud push over a trusted connection, the 102-byte datagram on a controlled LAN, real mobile-data WoL and post-reboot retention. **No auto-deployment** on router/NAS main networks.
4. Ship a second, explicitly opt-in Docker mode only after x86_64/ARM64 resource, license and security tests. Keep the existing official-router-plugin path and its data untouched.
